## 1. 背景与目标

v1.4 现状：引擎/数据已分离（`chips/registry.js` + UMD 数据文件自注册 **CHIP_REGISTRY**），但应用只取注册表第 `[0]` 颗芯片，数据文件靠 `index.html` 里手写的 `<script>` 标签加载——加第二颗芯片必须改 `index.html`，界面上也无法切换。

**目标**：一个包带 N 颗芯片，顶栏一选就切；未来开源时"贡献一颗芯片"的流程最简。

**成功标准（此前已确认）**：

1. 加新芯片 = 放入 1 个数据文件 + 清单加 1 行；`index.html` 从此不再改动；
2. 切换芯片 = 一个下拉 + 状态安全（不丢、不串、无确认弹窗）；
3. zip 离线版与 GitHub Pages 在线版同一套机制。

## 2. 决策记录（已定案）

| # | 决策 | 结论 | 要点 |
|---|------|------|------|
| D1 | 数据文件粒度 | **一份文件 = 一个具体封装型号** | 如 `wch-ch582m-qfn48.js`、未来 `wch-ch582f-qfn28.js` 各一份。接受少量重复；家族共享机制等真痛了再加（YAGNI）。CH582x 家族各封装（M=QFN48、F=QFN28…）都按此覆盖，发现问题再更新。 |
| D2 | 切换芯片时当前配置 | **各芯片各自留内存** | 会话内切换互不干扰、不弹确认、不做持久化；刷新即清空（与现状"刷新=清空"一致）；要留存用工程 JSON 导出。 |
| D3 | 加载机制 | **清单 + 动态注入 + 自注册** | `chips/manifest.js` 列清单；loader 动态注入 `<script>`；数据文件 UMD 自注册进 CHIP_REGISTRY。零构建、`file://` 可用、zip/Pages 同构。 |

## 4. 数据文件规范

### 4.1 命名

`chips/<vendor>-<chip>-<package 小写>.js`，如 `wch-ch582m-qfn48.js`。

### 4.2 结构（在 v1 基础上新增 `id`）

```jsonc
{
  "schemaVersion": 1,
  "id": "ch582m-qfn48",              // 新增：稳定唯一标识（状态键 / 工程 JSON 的 chipId）
  "meta": { "source": "...", "author": "...", "date": "..." },
  "chip": { "vendor": "WCH", "name": "CH582M", "package": "QFN48" },
  "package": { }, "pins": [ ], "globalConfigs": [ ], "resources": [ ]
}
```

- `id` 缺省回落 = `name`+`package` 的 slug（如 CH582M + QFN48 → `ch582m-qfn48`；兼容现有数据文件）；注册表检查唯一性，冲突者置灰"id 与 X 冲突"。
- 展示名（下拉框/状态栏）= `name · package`。
- UMD 尾巴不变（浏览器 push 注册表 / Node `module.exports`）——**现有数据文件零改动即可工作**（`id` 先按缺省回落，后续补显式值）。

## 5. 清单与加载器

### 5.1 `chips/manifest.js`

```js
window.CHIP_MANIFEST = ["chips/wch-ch582m-qfn48.js", /* 新增芯片在此加行 */];
```

顺序 = 下拉框顺序。指向不存在文件的条目 → 置灰"文件加载失败"。

### 5.2 `js/loader.js`

- **顺序注入**每个清单文件（保证"注册顺序 = 清单顺序"、逐文件可对账）：注入前记录注册表长度，`onload` 后比对新增项 → 得到该文件的产出（或"加载成功但未注册"= 语法错误等）。
- 产出 `window.CHIP_LOAD_PROMISE`：每文件 `{file, def | loadError}`。
- **失败隔离**：单文件失败 = 该条置灰，不影响其他芯片；全部失败 = 错误页逐条列出原因。
- 备注：芯片数大时（>10 颗）再评估并行注入等优化；当前顺序注入足够（YAGNI）。

## 6. 应用层改动（`js/app.js`）

- **启动**：等 `CHIP_LOAD_PROMISE` → 对每颗芯片跑 `validateChip` → 构建下拉（可用项 + 置灰项带原因）→ 默认选中第 1 颗可用芯片。
- **状态**：`histories[chipId]`（含各自撤销栈）；切换 = 换 def/history → 重建封装图 → 全量重绘。缩放/平移视图随切换重置（简单一致；per-chip 视图记忆列为未来可选项）。
- **顶栏**：`<select id="chip-select">`（标题右侧）；置灰项文案 `⚠ 文件名 —— 原因`。
- **版本闸门**：`validateChip` 改为 `schemaVersion ≤ 引擎支持上限`（当前上限 = 1）；超限置灰"此数据需要更新版本的工具"；错误信息保持人话。
- 状态栏与导出文件名沿用 `name · package`（现有 `baseName()` 已含）。

## 7. 工程 JSON 演进

- **导出**：增加 `chipId` 字段。
- **导入**：有 `chipId` → 芯片在包内则自动切到该芯片再应用；芯片不在包内 → 明确报错（提示缺哪颗芯片的数据文件）；无 `chipId`（v1 旧文件）→ 应用到当前选中芯片（向后兼容；v1 文件天然对应 CH582M/QFN48）。

## 8. schemaVersion 演进机制

- 引擎声明支持上限（当前 1）；数据 > 上限 → 置灰拒绝（人话原因）。
- 数据 < 上限：引擎负责兼容读取（未来 v2 到来时在引擎内做迁移/兼容分支，并在此补规范）。
- 本次改动仅一处：闸门从"必须 = 1"升级为"≤ 上限"。

## 9. 贡献流程（面向开源；配套 #4 发布时写进 README）

1. 复制模板（后续提供 `chips/_template.js`；当前 = 复制任一现有数据文件）；
2. 填 `meta/chip/pins/resources`；
3. 放入 `chips/`，**清单加一行**——两步缺一不可。`file://` 无法列目录，"忘加清单行"该芯片不会出现且无技术手段可检测（只能靠流程文档强调）；"忘放文件"则会被置灰捕获；
4. 本地双击 `index.html` 验证 → 提 PR。

## 10. 测试计划

- **Node 单测**（随实现 TDD）：`id` 唯一/缺省回落；版本闸门（>上限拒绝、≤接受）；loader 对账纯逻辑（抽成可测函数）；histories 隔离。
- **浏览器实测**（每批改动必过）：原型 6 场景（T1–T6，见测试清单）+ 真实鼠标路径原则（沿用 v1.1 教训）。
- **回归**：现有 91 单测 + 8000 次 fuzz 全绿不变；导出/导入往返含 `chipId`。

## 11. 非目标（本子项目不做）

- localStorage/工程自动持久化；芯片搜索/分组/最近使用；
- optional signals（#2）；BGA/新封装族渲染（#3）；发布打包与分发（#4，方向已定：Pages + zip + Inno 安装器 + update.bat，见附录 §13）；
- per-chip 视图（缩放/平移）记忆。

## 12. 风险与缓解

- 清单漏行 → 芯片不出现（无技术检测手段；流程文档强调两步，见 §9）；
- 芯片多时顺序注入启动稍慢 → >10 颗时再优化；
- 第三方浏览器差异 → 发布前 Firefox/Safari 冒烟（Chromium 已验证）。
